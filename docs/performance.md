# Performance and benchmarking

TorrentPlayer has a repeatable streaming benchmark and a separate WebView playback probe. Run release
builds. The streaming benchmark measures when requested bytes are ready; it does not decode
video. The WebView probe measures decoded frames and seeks on the installed Windows app.

## Metrics and interpretation

| Metric              | Definition                                                                              | Target on a healthy swarm |
| ------------------- | --------------------------------------------------------------------------------------- | ------------------------- |
| Data-ready startup  | Time from starting a stream until its startup byte ranges are available                 | < 3 s                     |
| Data-ready seek     | Time from a seek until the requested range is available                                 | < 1.5 s                   |
| Decoded first frame | Time from the playback action until a video frame is presented                          | < 3 s                     |
| Decoded seek        | Time from a seek until a frame at the destination is presented while playing            | < 1.5 s                   |
| Stalls              | Count and total duration while simulated or actual playback waits for data              | 0 on a healthy swarm      |
| Dropped frames      | Browser playback-quality counters, reported separately during steady playback and seeks | Machine dependent         |

Compare both engines with the same bandwidth, latency, fixture, and number of runs. Report
median and p95, peer counts, throughput, and stalls. Five startup samples give a descriptive p95,
not a stable estimate of rare slow starts. Loopback results exclude VPN overhead and peer
discovery on the public internet. Desktop activity can affect measurements on a shared machine.

## Repeatable streaming matrix

```sh
cargo build -p torrentplayer-bench --release
python3 scripts/benchmark-streaming.py --scenario healthy --scenario constrained \
  --scenario high-latency --scenario peer-dropout --runs 5
```

Each case starts five independent download sessions with empty caches. A deterministic local
seeder supplies generated bytes through the real streaming server. Each run seeks to 10%, 50%,
90%, and 25%. Each seek is measured in its own session from an empty download directory (start
up, watch, then seek once), so no seek lands on data downloaded for an earlier one;
`torrentplayer-bench --shared-cache` restores the older single-session seeks. Results recorded before
2026-10-19 used one session per run. The default media workload consumes 1 MiB/s from a
256 MiB file.

| Scenario     | Link cap              | RTT              | Peer behavior                             |
| ------------ | --------------------- | ---------------- | ----------------------------------------- |
| Healthy      | 8 MiB/s               | 40 ms            | One seeder                                |
| Constrained  | 2 MiB/s               | 40 ms            | One seeder                                |
| High latency | 2 MiB/s               | 150 ms           | One seeder                                |
| Peer dropout | 2 MiB/s and 0.5 MiB/s | 60 ms and 120 ms | Faster peer disappears during seconds 3–8 |

The dropout leaves less bandwidth than playback consumes. A stall in this case is not by itself
a regression: compare stall duration, recovery, and buffer behavior between engines.

The runner saves every command, case configuration, binary/source hashes, raw measurements,
logs, and an HTML report under `target/streaming-benchmarks/`. Use `--out` to choose a new folder.
A failing or timed-out case remains visible in the report. Do not replace the benchmark binary
while a matrix is running. The fixture generator uses a fixed 1 MiB working buffer rather than
allocating the whole file in memory.

## 4K-rate and large-file workloads

```sh
python3 scripts/benchmark-streaming.py --scenario 4k-rate --scenario large-file --runs 5
```

These use 2 GiB and 8 GiB files with a 6 MiB/s media rate (about 50 Mb/s), a 16 MiB/s link,
40 ms RTT, 8 MiB startup ranges at both ends, and 8 MiB seek ranges. They exercise large offsets,
file allocation, startup, and seeking without requiring a multi-gigabyte encoded video. They
measure the storage and streaming path; run the decoder probe as well to assess actual 4K video.

Use the native Windows release binary to include Windows filesystem behavior. The runner also
accepts a Windows `.exe` path from WSL and translates the output paths:

```sh
python3 scripts/benchmark-streaming.py --binary target/agent-net/release/torrentplayer-bench.exe \
  --scenario 4k-rate --scenario large-file --runs 5
```

Allow space for the seed plus one destination file, roughly 16 GiB for the largest case, and
some overhead. Benchmark download and seeder directories are temporary and removed afterwards.

## Actual 4K decoding

Generate a reproducible 10-second H.264 test pattern with FFmpeg:

```sh
ffmpeg -f lavfi -i testsrc2=size=3840x2160:rate=30 -t 10 -c:v libx264 \
  -preset ultrafast -b:v 50M -minrate 50M -maxrate 50M -bufsize 100M \
  -x264-params nal-hrd=cbr:force-cfr=1 -pix_fmt yuv420p -g 60 \
  -movflags +faststart -threads 4 -an 4k-pattern.mp4
python3 scripts/serve-benchmark-media.py 4k-pattern.mp4
```

Start the installed Windows app with a disposable `TORRENTPLAYER_PROFILE_DIR`, its own
`WEBVIEW2_USER_DATA_FOLDER`, and `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=46129`.
Use direct networking for this decoder-only test. The profile must contain exactly one queue
item with ID `benchmark-fixture`; the probe refuses a personal queue. Then run native Windows Node:

```sh
node scripts/benchmark-player.mjs decoder4k-run-1.json decoder4k
```

Repeat five times. This decodes the generated 3840×2160 video through the same WebView runtime,
served on loopback port 46128. It records first frame, seeks to 50%, 90%, and 25%, waiting events,
and dropped frames. The three-second initial watch window reports steady playback separately
from seek settling. The OS file cache is warm; these numbers do not represent torrent startup.
Close the disposable app and loopback server afterwards. Never run two active WireGuard tunnels
with the same peer credentials during a live network measurement.

For a public-swarm smoke check, queue an openly licensed fixture such as Big Buck Bunny and use
`playback` in place of `decoder4k`. This downloads real video data; use a capped, disposable
profile, remove its downloads afterwards, and keep stream URLs (which contain session tokens)
out of logs and reports. A single successful smoke check is not a public-swarm percentile.

## Incoming peers, download limits, and the saved DHT

Three measurements cover the network changes in 0.3.0. Run them with a release build; the
first two are local and deterministic, the third needs the public DHT.

**Incoming peers.** `--inbound` makes the viewer reachable only from outside: it accepts
incoming connections (the swarm engine through the network manager's listener, as with
`network.incomingPeers`; librqbit on its own listener) and announces its port to a local
tracker that lists no seeders. Each seeder connects to the viewer as soon as the tracker has
its address, through the same link shaping as outgoing connections (shared downlink, half the
round trip on every chunk, the viewer's handshake included). Compare it with outgoing peers
found through the same tracker:

```sh
torrentplayer-bench local --engine swarm --seeders 4 --upload-mibps 2 --rtt-ms 60 --tracker-interval 30
torrentplayer-bench local --engine swarm --seeders 4 --upload-mibps 2 --rtt-ms 60 --inbound
```

Seeders dial the viewer the moment it announces, so this is the best case for incoming peers:
in a real swarm they find the viewer at their next announce or DHT lookup. Both engines listen
on every interface, so Windows may show a firewall prompt; the loopback traffic does not need
it. `peers_seen` counts addresses the engine learned, so incoming-only runs may report 0.

**Download-limit accuracy.** `limit` adds a local torrent with a download limit, selects the
file (both engines then download it in the background), lowers the limit after
`--change-after` seconds, and samples the engine every 100 ms:

```sh
torrentplayer-bench limit --engine swarm --limit-mibps 2 --then-mibps 1 --churn 8 --runs 3
```

By default eight seeders share a 16 MiB/s downlink, so only the limit holds the rate back, and
`--churn 8` takes each seeder offline for 2 s of every 8 s, staggered. The report gives the
delivered rate (verified bytes per second) and the engine's reported `download_bps` over the
second half of each phase, the highest and lowest one-second delivered rate after the change
(a burst, and a dip while the limiter's debt is repaid), the bytes delivered in the two seconds
after it beyond the new limit, and the time until every later two-second window stays within
5% of the new limit and of the rate it settled at (with churn the rate can settle below the
limit). The reported rate is already smoothed by the engine, so its settling time uses each
sample.
The fixture uses 16 KiB pieces so that one piece is under 2% of a one-second window at 1 MiB/s.

**Saved DHT state.** `--dht-state DIR` keeps the swarm engine's DHT routing tables in `DIR`
(`swarm.json`), set through the same engine option the app uses for its data folder. librqbit
keeps none, as in the app since 49626d2 (see the measurements below), so for it the option
changes nothing. A session without a saved file starts cold and saves one when it stops.
`--no-trackers` leaves the DHT as the only peer source. Prime the folder with one run, then compare against runs without the
option, one start-up and one seek each:

```sh
torrentplayer-bench torrent "magnet:?xt=urn:btih:08ada5a7a6183aae1e09d831df6748d566095a10&dn=Sintel" \
  --engine rqbit --runs 1 --seeks 0.5 --download-mibps 10
torrentplayer-bench torrent sintel.torrent --engine swarm --no-trackers --no-web-seeds \
  --runs 1 --seeks 0.5 --download-mibps 10 [--dht-state DIR]
```

The swarm engine does not open magnet links itself (the app fetches their metadata with
librqbit), so it plays the same torrent from its `.torrent` file with trackers and web seeds
off. `first peer` is the time from adding the torrent to the first connected peer. librqbit adds
a magnet link only once it has the metadata, which already needs a peer, so for magnet links
sampling starts after the metadata arrived and the metadata time is the measure to compare.

## Through a VPN or proxy

Public-swarm runs (`torrent`, and the torrents and magnet links of `suite`) can go through the
app's protected network modes instead of connecting directly, to measure what users of those
modes get:

```sh
torrentplayer-bench torrent sintel.torrent --engine swarm --runs 1 --wireguard wg0.conf
TORRENTPLAYER_BENCH_SOCKS5_PASSWORD=... torrentplayer-bench torrent sintel.torrent \
  --socks5 proxy.example:1080 --socks5-user me
cargo bench-suite my-files.txt --public --wireguard wg0.conf
```

- `--wireguard FILE` reads a WireGuard `.conf` with the app's parser and runs both engines
  through TorrentPlayer's built-in tunnel, as the app's WireGuard mode does.
- `--socks5 HOST:PORT` (with `--socks5-user`; the password comes from
  `TORRENTPLAYER_BENCH_SOCKS5_PASSWORD`, never the command line) uses the app's SOCKS5 mode
  with its defaults: host names, trackers, and DHT through the proxy.

Each engine gets its own network manager, verified before the run starts: a tunnel or proxy that
does not let traffic through within 30 seconds fails the run with the network's reason instead
of being measured as a slow swarm. The kill switch stays on, so nothing leaves outside the
tunnel or proxy. As in the app, librqbit then has no DHT, listener, or UDP of its own and reaches
peers through the network's loopback bridge, so it finds fewer peers than torrentplayer-swarm,
whose DHT and UDP trackers use the tunnel or the proxy's UDP relay. The app also hands
librqbit peers it found through scoped DHT and UDP trackers; the bench does not, so for librqbit
magnet links this is a lower bound. Local media (`local`, and local entries of `suite`) always
runs directly: a tunnel cannot reach seeders on `127.0.0.1`. The suite report names the mode
and endpoint (never keys or passwords). The app's former bind-to-adapter VPN mode no longer
exists; to measure a VPN app, connect it system-wide and run without these options.

## Benchmark your own files

`cargo bench-suite` runs the streaming benchmark on a list of your own media files, torrents,
and magnet links, and writes a report. Each local file is seeded on `127.0.0.1` through the same
link emulator as the generated fixture, so nothing leaves the machine.

```sh
cargo bench-suite my-files.txt --quick     # 1 run, 2 scenarios: a few minutes per file
cargo bench-suite my-files.txt             # the full matrix: about 20 minutes per file
cargo bench-suite my-files.txt public      # also run the torrents and magnet links (peers only)
cargo bench-suite my-files.txt public --web-seeds   # plus a swarm-engine row with web seeds
cargo bench-file "D:\Videos\My Lecture.mkv" --upload-mibps 4 --seeders 2   # one file, one scenario
```

The aliases (in `.cargo/config.toml`) build `torrentplayer-bench` in release mode and run
`suite` and `local --media`. A list has one entry per line:

```text
# Comments start with #; blank lines are ignored.
D:\Videos\My Lecture 01.mkv | lecture 1
clips/talk.mp4
https://webtorrent.io/torrents/sintel.torrent | Sintel
magnet:?xt=urn:btih:...
downloads/some.torrent
```

The whole line is the entry, so Windows paths with spaces need no quotes (quotes from "Copy as
path" are removed). ` | label` names the entry in the report. Relative paths are relative to
the list file. Lines ending in `.torrent` are torrent files; `https://` links must point to a
`.torrent` file. `crates/torrentplayer-bench/lists/example.txt` has commented examples.

**Local files** run both engines on a local swarm: links of 2, 8, and 25 MiB/s (the viewer's
downlink, shared by the seeders) × 1 or 4 seeders at 40 ms round trip, plus 8 MiB/s with 4
seeders at 120 ms; 3 runs each, seeking to 10%, 50%, 90%, and 25% of the duration, each seek
in its own session. 2 MiB/s is a slow home connection, 25 MiB/s a fast one, and the 120 ms row
a distant swarm. `--quick` runs once, with 2 MiB/s and 1 seeder and 25 MiB/s and 4 seeders.
`--links 2,8`, `--seeders 1,4`, `--rtt-ms 40`, `--runs N`, and `--engines rqbit,swarm` change
the matrix; other `torrentplayer-bench` options (`--seeks`, `--watch`, `--piece-kib`,
`--download-mibps`, scheduler tuning) apply to every run. The file is hashed once and seeded
in place without being modified; each run downloads into a temporary folder that is deleted
afterwards.

Start-up and seeks follow the file's container, read with TorrentPlayer's own parsers
(`torrentplayer-media`), instead of a flat 1 MiB at each end:

- **Start-up** reads the header in the order a player does, one read after the other: for MP4
  and MOV, the top-level boxes up to `moov` (only the header of an `mdat` before it), so a file
  with `moov` at the end needs a read at the tail before any media; for Matroska and WebM,
  everything before the first `Cluster`. Then one second of media (at the file's average
  bitrate) from where the media data starts.
- **Seeks** go to a fraction of the duration. The player starts at the keyframe at or before the
  target (MP4 sync samples, Matroska cue points) and needs the media from there through the
  target plus one second. A Matroska file with `Cues` after the clusters reads them before its
  first seek, as FFmpeg-based players do.

The duration comes from the container and sets the read-ahead, as `--duration` does. Fragmented
MP4, files without a keyframe index, and other containers fall back to the flat reads; the
report says so. `--startup-mib` and `--seek-mib` force the flat reads.

**Torrents and magnet links** play from their public swarm with both engines, a 10 MiB/s
download limit (`--download-mibps`), 3 runs, and the same seeks. They download from and upload
to other people's computers, which see your IP address, so the suite skips them unless the
command includes `public` or `--public`, and prints a notice before it starts. Only list
content you have the right to download and share; this project uses openly licensed films
(such as the Blender open movies) and free-software images for public runs.

Public rows use peers only. Many torrents also list HTTP web seeds (BEP 19 `url-list`, or `ws=`
in a magnet link): the WebTorrent copies of the Blender films each list one. The swarm engine
can download from them and librqbit cannot, so with web seeds a public row would partly measure
a web server and the engine comparison would be unfair. The suite downloads a linked `.torrent`
once per entry, reports its trackers and web seeds on the "Torrent" line, and runs the swarm
engine without web seeds. `--web-seeds` adds a separate swarm row, labelled _peers + web
seeds_, that uses them. For a peers-only baseline, prefer torrents without web seeds, such as
the Ubuntu release images (the 24.04.3 server image lists none). The swarm engine opens only
`.torrent` files, so magnet links run with librqbit only.

The results go to `bench-results/<UTC timestamp>/` (git-ignored; `--out DIR` to choose):

- `report.md`: a guide to reading it, then for each entry the media line (container, video and
  audio codecs, duration, bitrate, size, where the index is, header size, keyframes) or the
  torrent line (size, files, trackers, web seeds), how start-up and seeks read the file, any
  warnings, a verdict, and a table with one row per engine and scenario: start-up and seek
  latency (median / p95 in ms), throughput (median of each run's average download rate), peers
  per run (live at the end / seen during the run), and stalls while watching.
- `results.json`: every run, with each start-up read, seek target, keyframe, and byte count.

The terminal shows the verdicts and a summary at the end, and the reports are rewritten after
each entry, so an interrupted suite keeps what it finished. An entry that fails is reported and
the suite continues; the exit code is non-zero if anything failed.

### Reading the report

The guide at the top of `report.md` says the same as this section.

- **Start-up** is the time from pressing play until the player has the bytes it needs for the
  first frame: the container header, wherever it is, and about a second of media. **Seek** is
  the time from a seek until the data from the keyframe before the target through one second
  past the target has arrived. Both are data-ready times at the stream server, not decoding or
  the first frame on screen, which add a little on top.
- **Targets** on a healthy swarm: median start-up under 3 s and median seek under 1.5 s. Each
  entry's verdict counts the rows that meet both and names the slowest start-up and seek.
- **Median and p95:** the median is the typical case, p95 nearly the worst. With 3 runs (12
  seeks) p95 is close to the maximum, so one slow run moves it.
- **Local scenarios** run on this machine and repeat well. The link speed is the viewer's
  downlink, shared by all seeders: 2 MiB/s is a slow home connection, 8 a typical one, 25 a
  fast one (a 1080p film needs about 1). Seeders hold the whole file; the round trip to each is
  40 ms (nearby) or 120 ms (far away).
- **Public swarms** are real peers on the internet and vary from run to run and day to day.
  Rows are peers only unless marked _peers + web seeds_. _Peers per run_ is live at the end /
  seen during the run; a handful (the verdict flags fewer than 5) means a thin swarm whose
  result depends on a few peers.
- **Comparing engines:** compare librqbit and the swarm engine within one scenario, not across
  scenarios. With few runs, differences under about 15%, or with overlapping median-to-p95
  ranges, are likely noise; rerun with `--runs 5` before drawing conclusions.
- **Containers:** an MP4 with `moov` at the end needs a read at the end of the file before any
  media, so it starts slower than the same file with `moov` first (remux with
  `ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4`); a Matroska file reads its Cues
  before the first seek when they come after the media. The line under each file says what
  start-up and seeks read.
- **Seeks of a few milliseconds** mean the data was already downloaded: each seek follows three
  seconds of watching (`--watch`), and on a fast link a short file can be complete by then.
  **Stalls** count the times playback ran out of data while watching.

## Tuning and regression checks

`--queue-ms` overrides the swarm engine request window for an explicit comparison. Keep the
baseline binary, fixture, network shape, and run count fixed. Change a production default only
when repeated measurements improve the relevant workload without worsening stalls or tails.
The default matrix is a developer tool; it is not currently enforced as a CI performance gate.

Press **D** in the player to show live metrics and the piece map.

8073ce9 made the reported rate match the delivered one before the change (it overstated it by
19% with 40 churning peers) and removed the excess with eight peers. With 40 peers lowering the
limit still released about 1.5 MB within 200 ms, as waiting readers returned at once, and the
kept debt was then repaid by delivering nothing for more than a second (1.4 s in the run
inspected), long enough to stall playback. Verified data also fell to 0.62–0.76 MiB/s under the
1 MiB/s limit: the queue sizing let 40 peers hold more requests than the limit delivers before
the 8 s request timeout, and blocks fetched again after a timeout arrived twice.
