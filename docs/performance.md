# Performance and benchmarking

TorrentPlayer has a repeatable streaming benchmark and a separate WebView playback probe. Run release
builds. The streaming benchmark measures when requested bytes are ready; it does not decode
video. The WebView probe measures decoded frames and seeks on the installed Windows app.

## Metrics and interpretation

| Metric              | Definition                                                                              | Target on a healthy swarm |
| ------------------- | --------------------------------------------------------------------------------------- | ------------------------- |
| Data-ready startup  | Time from starting a stream until its startup byte ranges are available                 | < 3 s                     |
| Data-ready seek     | Time from a seek until the requested range is available                                 | < 1.5 s                   |
| Decoded first frame | Time from the playback action until a video frame is presented                          | < 3 s                     |
| Decoded seek        | Time from a seek until a frame at the destination is presented while playing            | < 1.5 s                   |
| Stalls              | Count and total duration while simulated or actual playback waits for data              | 0 on a healthy swarm      |
| Dropped frames      | Browser playback-quality counters, reported separately during steady playback and seeks | Machine dependent         |

Compare both engines with the same bandwidth, latency, fixture, and number of runs. Report
median and p95, peer counts, throughput, and stalls. Five startup samples give a descriptive p95,
not a stable estimate of rare slow starts. Loopback results exclude VPN overhead and peer
discovery on the public internet. Desktop activity can affect measurements on a shared machine.

## Repeatable streaming matrix

```sh
cargo build -p torrentplayer-bench --release
python3 scripts/benchmark-streaming.py --scenario healthy --scenario constrained \
  --scenario high-latency --scenario peer-dropout --runs 5
```

Each case starts five independent download sessions with empty caches. A deterministic local
seeder supplies generated bytes through the real streaming server. Each run seeks to 10%, 50%,
90%, and 25%. Each seek is measured in its own session from an empty download directory (start
up, watch, then seek once), so no seek lands on data downloaded for an earlier one;
`torrentplayer-bench --shared-cache` restores the older single-session seeks. Results recorded before
2026-10-19 used one session per run. The default media workload consumes 1 MiB/s from a
256 MiB file.

| Scenario     | Link cap              | RTT              | Peer behavior                             |
| ------------ | --------------------- | ---------------- | ----------------------------------------- |
| Healthy      | 8 MiB/s               | 40 ms            | One seeder                                |
| Constrained  | 2 MiB/s               | 40 ms            | One seeder                                |
| High latency | 2 MiB/s               | 150 ms           | One seeder                                |
| Peer dropout | 2 MiB/s and 0.5 MiB/s | 60 ms and 120 ms | Faster peer disappears during seconds 3–8 |

The dropout leaves less bandwidth than playback consumes. A stall in this case is not by itself
a regression: compare stall duration, recovery, and buffer behavior between engines.

The runner saves every command, case configuration, binary/source hashes, raw measurements,
logs, and an HTML report under `target/streaming-benchmarks/`. Use `--out` to choose a new folder.
A failing or timed-out case remains visible in the report. Do not replace the benchmark binary
while a matrix is running. The fixture generator uses a fixed 1 MiB working buffer rather than
allocating the whole file in memory.

## 4K-rate and large-file workloads

```sh
python3 scripts/benchmark-streaming.py --scenario 4k-rate --scenario large-file --runs 5
```

These use 2 GiB and 8 GiB files with a 6 MiB/s media rate (about 50 Mb/s), a 16 MiB/s link,
40 ms RTT, 8 MiB startup ranges at both ends, and 8 MiB seek ranges. They exercise large offsets,
file allocation, startup, and seeking without requiring a multi-gigabyte encoded video. They
measure the storage and streaming path; run the decoder probe as well to assess actual 4K video.

Use the native Windows release binary to include Windows filesystem behavior. The runner also
accepts a Windows `.exe` path from WSL and translates the output paths:

```sh
python3 scripts/benchmark-streaming.py --binary target/agent-net/release/torrentplayer-bench.exe \
  --scenario 4k-rate --scenario large-file --runs 5
```

Allow space for the seed plus one destination file, roughly 16 GiB for the largest case, and
some overhead. Benchmark download and seeder directories are temporary and removed afterwards.

## Actual 4K decoding

Generate a reproducible 10-second H.264 test pattern with FFmpeg:

```sh
ffmpeg -f lavfi -i testsrc2=size=3840x2160:rate=30 -t 10 -c:v libx264 \
  -preset ultrafast -b:v 50M -minrate 50M -maxrate 50M -bufsize 100M \
  -x264-params nal-hrd=cbr:force-cfr=1 -pix_fmt yuv420p -g 60 \
  -movflags +faststart -threads 4 -an 4k-pattern.mp4
python3 scripts/serve-benchmark-media.py 4k-pattern.mp4
```

Start the installed Windows app with a disposable `TORRENTPLAYER_PROFILE_DIR`, its own
`WEBVIEW2_USER_DATA_FOLDER`, and `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=46129`.
Use direct networking for this decoder-only test. The profile must contain exactly one queue
item with ID `benchmark-fixture`; the probe refuses a personal queue. Then run native Windows Node:

```sh
node scripts/benchmark-player.mjs decoder4k-run-1.json decoder4k
```

Repeat five times. This decodes the generated 3840×2160 video through the same WebView runtime,
served on loopback port 46128. It records first frame, seeks to 50%, 90%, and 25%, waiting events,
and dropped frames. The three-second initial watch window reports steady playback separately
from seek settling. The OS file cache is warm; these numbers do not represent torrent startup.
Close the disposable app and loopback server afterwards. Never run two active WireGuard tunnels
with the same peer credentials during a live network measurement.

For a public-swarm smoke check, queue an openly licensed fixture such as Big Buck Bunny and use
`playback` in place of `decoder4k`. This downloads real video data; use a capped, disposable
profile, remove its downloads afterwards, and keep stream URLs (which contain session tokens)
out of logs and reports. A single successful smoke check is not a public-swarm percentile.

## Tuning and regression checks

`--queue-ms` overrides the swarm engine request window for an explicit comparison. Keep the
baseline binary, fixture, network shape, and run count fixed. Change a production default only
when repeated measurements improve the relevant workload without worsening stalls or tails.
The default matrix is a developer tool; it is not currently enforced as a CI performance gate.

Press **D** in the player to show live metrics and the piece map.

## Measurements from 18 October 2026

Release builds on a Windows 11 desktop test machine (8-core CPU, discrete GPU), WebView2 155. Baseline cases ran under WSL; 2 GiB and 8 GiB cases ran natively
on Windows/NTFS. Five runs per case, one peer except the two-peer dropout case.
Download caches were empty; OS caches were not flushed. Values below are seconds, median / p95.

| Scenario     | Engine | Startup      | Seek        | Time stalled |
| ------------ | ------ | ------------ | ----------- | ------------ |
| healthy      | rqbit  | 0.30 / 0.30  | 0.40 / 0.43 | 0.0%         |
| healthy      | swarm  | 0.30 / 0.31  | 0.37 / 0.40 | 0.0%         |
| constrained  | rqbit  | 1.03 / 1.06  | 1.62 / 1.75 | 0.0%         |
| constrained  | swarm  | 1.04 / 1.04  | 1.03 / 1.15 | 0.0%         |
| high-latency | rqbit  | 1.26 / 1.27  | 1.62 / 1.75 | 0.0%         |
| high-latency | swarm  | 1.26 / 1.28  | 1.03 / 1.18 | 0.0%         |
| peer-dropout | rqbit  | 1.41 / 1.42  | 4.99 / 6.67 | 8.0%         |
| peer-dropout | swarm  | 1.26 / 1.33  | 1.23 / 3.04 | 5.7%         |
| 4k-rate      | rqbit  | 2.83 / 2.90  | 1.74 / 1.97 | 0.0%         |
| 4k-rate      | swarm  | 1.72 / 1.72  | 1.00 / 1.03 | 0.0%         |
| large-file   | rqbit  | 6.85 / 35.97 | 1.71 / 1.94 | 0.0%         |
| large-file   | swarm  | 1.72 / 1.74  | 1.02 / 1.04 | 0.0%         |

The independent 4K decoder probe (five runs, warm local file cache) measured 14.4 / 19.5 ms to first frame and 67.8 / 91.2 ms for seeks. Initial steady playback dropped 1 of 451 frames; watched intervals including seek settling dropped 17 of 706.

These short measurements establish functional coverage and comparative data readiness. They do
not establish sustained 4K performance over a public VPN or every codec. The separate Big Buck
Bunny WireGuard smoke check rendered a first frame 1.36 s after the app player-start marker
(metadata fetch excluded). Two isolated-profile follow-up requests timed out; later normal-profile
connection and search checks succeeded. No public-swarm percentile is inferred.

Raw JSON, commands, binary hashes, and the combined HTML report are saved locally under
`target/streaming-benchmarks/`, with the overview at `target/streaming-benchmarks/report.html`.
Production request-window defaults were retained; no A/B tuning claim is made.
